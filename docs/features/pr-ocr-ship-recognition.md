# 舰船识别 OCR 与智能换船可靠性调研报告

本文说明 FastOCR 舰船识别方案的选型依据，以及智能换船一期为什么采用物理槽位快照、
四级 OCR 累积和主选托底流程。完整三阶段测试方法与详细数据见
[`docs/features/ocr-ship-recognition.md`](ocr-ship-recognition.md)。

## 1. 结论

本次 PR 采用以下方案：

1. 增加基于 MaaFramework FastOCR 的可选船只 OCR 引擎；
2. 使用 PP-OCRv6-small 检测、识别模型及字典，资源合计 31,114,872 字节；
3. `enhanced_ship_ocr` 默认关闭，关闭时继续使用现有 EasyOCR 链路；
4. 准备页等级和舰种使用针对 1280x720 校准的固定区域；
5. 船池中的舰名、舰种和等级按同一张卡片坐标绑定；
6. 候选舰船逐卡读取约束信息，避免按 OCR 返回行号或顺序拼接属性；
7. 准备页以四级快照逐字段累积结果，后续失败不得覆盖已经确认的字段；
8. 已在编队且满足当前规划规则的槽位直接标记为已验证，不再进入船池；
9. 主选身份无法确认时先使用备选托底，再对主选执行一次有限回查。

FastOCR 并非在所有 OCR 场景中替换 EasyOCR。它只在用户主动开启增强船只识别后，
用于舰船相关识别节点。智能换船一期也不依赖无限重试：每级 OCR 和主选回查都有固定
次数，失败后明确保留备选或退出。

## 2. 问题背景

原链路在小字号舰船信息上主要存在三类问题：

- 准备页等级区域包含过多空白或相邻元素，可能把 `Lv.1` 识别为 `Lv.11`；
- 船池舰种、等级与舰名按返回顺序组合，同一行有多个候选时可能发生属性错位；
- 识别到同名候选后缺少卡片级约束校验，可能点击舰种或等级不符合规则的卡片；
- 首次快照缺少舰种和等级时，已在正确位置的舰船仍可能被重新选择；
- 主选连续识别失败后缺少稳定终点，可能重复执行“选不到、重选、仍选不到”。

这些问题不能只依靠更换 OCR 模型解决。模型、裁剪区域、输入预处理和识别结果的坐标
绑定必须一起验证；换船决策还必须使用有限重试、字段独立累积和明确退出路径。

## 3. 方案调研

### 3.1 行业方案调研

本次选型调研参考 mirrorchyan 镜像站收录的 50 余个主流开源手游自动化项目，按技术
路线归纳如下：

| 路线 | 代表 | 主要特征 |
|---|---|---|
| MaaFramework 系 | MAA、PalsAssistant 等 | C++ 实现，模板匹配为主，FastOCR（PP-OCR）辅助 |
| ALAS 系 | AzurLaneAutoScript | Python 实现，以专训 OCR 模型为核心 |
| 独立 Python 系 | BAAS、BAAH 等 | 模板匹配结合 RapidOCR 或独立 OCR 服务 |
| PC 后台系 | ok-script 系 | PP-OCR 转 ONNX，使用 OpenVINO 或 NPU 加速 |
| 安卓端 | ArkLights 等 | 无障碍截图结合 PaddleOCR |
| 专用 OCR | LuLing-OCR | 面向战舰少女 R 生态训练的 CRNN 模型 |

调研得到的共同实践是：

1. 静态 UI 优先模板匹配，动态名称和数值才使用 OCR；
2. 无损截图和先裁剪 ROI 是识别可靠性的基础；
3. PP-OCR 的 ONNX 推理已成为通用 OCR 主流方案；
4. 小字识别需要放大、字符集约束和易混字符纠错，预处理不能默认视为正向收益；
5. 识别结果必须按画面坐标绑定，不能依赖 OCR 返回顺序；
6. 固定分辨率与有限缓存、重试是自动化流程稳定运行的前提。

这些结论对应本次工程决策：使用 PP-OCRv6-small、按 1280x720 校准 ROI、通过真实数据
选择原图而非 Otsu、按物理卡片和槽位保存属性，并为连续识别失败设计有限托底路径。

### 3.2 OCR 候选方案

本次实测覆盖：

- MaaFramework FastOCR：PP-OCRv5 mobile/server、PP-OCRv6 tiny/small/medium；
- RapidOCR 3.9.2：PP-OCRv6-small recognition-only；
- EasyOCR：默认参数和船只小字优化参数；
- LuLing-OCR：原始 PyTorch 模型；
- 原图与逐 ROI Otsu 二值化两种输入。

测试同时使用 ADB 无损截图和 scrcpy H264 截图，所有组合重复三轮。测试重点不是判断
某个引擎的通用能力，而是确定它在战舰少女 R 1280x720 舰船小字场景中的表现。

### 3.3 等级识别结果

每种输入的统计口径为：

```text
4 支舰队 x 2 种截图源 x 6 个槽位 x 3 轮 = 144 次
```

关键结果如下：

| 方案 | 非二值化 | Otsu | 主要结论 |
|---|---:|---:|---|
| FastOCR + PP-OCRv6-small | 144/144 | 144/144 | 两种输入均无错误 |
| RapidOCR + PP-OCRv6-small | 138/144 | 144/144 | 原图固定误读 `Lv.1` |
| EasyOCR 优化参数 | 138/144 | 144/144 | 二值图准确，但耗时更高 |
| EasyOCR 默认参数 | 69/144 | 132/144 | 小字场景错误较多 |
| LuLing-OCR | 54/144 | 72/144 | 字符混淆较多 |

FastOCR + PP-OCRv6-small 在非二值化输入下平均耗时 6.84ms，P95 为 7.13ms。
EasyOCR 优化参数在二值图上平均耗时 31.06ms，约为前者的 4.5 倍。

因此等级生产链路选择 FastOCR、校准后的原图 ROI，不增加 Otsu 预处理。

### 3.4 舰种识别结果

舰种测试使用校准后的 ROI，并比较 X4 原图与 X4 Otsu 输入。静态截图和 120 次实机
舰队切换合计得到每种引擎 1320 个双源有舰槽样本。

| 方案 | X4 原图 | X4 Otsu | 平均耗时/槽 |
|---|---:|---:|---:|
| FastOCR | 1320/1320 | 1200/1320 | 10.47ms |
| EasyOCR 优化参数 | 1320/1320 | 1233/1320 | 14.57ms |
| EasyOCR 默认参数 | 1320/1320 | 1260/1320 | 34.63ms |

三种引擎在 X4 原图上均无错误，但 FastOCR 平均耗时最低。Otsu 对舰种文字造成稳定
负向影响，因此舰种生产链路使用 X4 原图。

## 4. 工程实现

### 4.1 引擎与模型

`FastOCREngine` 通过 MaaFramework FastOCR 加载内置模型，使用 CPU 执行器，主要参数为：

```python
only_rec=False
threshold=0.3
```

模型放在 `autowsgr/data/ocr/ppocr_v6_small/`，随包分发，首次运行不需要联网下载。
模型来自 MaaXYZ/MaaCommonAssets，对应 MIT 许可证随资源一并提交。

### 4.2 兼容与回退

配置项如下：

```yaml
ocr:
  enhanced_ship_ocr: false
```

- `false`：不创建 FastOCR 实例，保持现有 EasyOCR 行为；
- `true`：船只相关节点优先使用 FastOCR；
- FastOCR 不替换章节、阵型等其他 OCR 节点。

### 4.3 区域校准与统一解析

- 准备页六个等级和舰种区域使用固定的 1280x720 归一化坐标；
- 船池等级裁剪偏移为 `(-62, -38, -2, -20)`；
- 船池舰种裁剪偏移为 `(-62, -59, -13, -34.5)`；
- 船池小字按 2、3、4 倍逐级尝试；
- 等级共享字符纠错和 1 至 110 范围校验；
- 舰种共享允许字符集合和标准化规则。

### 4.4 卡片坐标绑定

船池识别先记录舰名中心坐标与卡片行标识，再从同一卡片读取等级和舰种。候选卡片
逐张校验，只有名称命中且已声明约束符合时才进入点击流程。这样可避免以下错误：

- 同一行两张卡片的舰名和等级交叉组合；
- OCR 返回顺序变化导致舰种绑定到另一张卡片；
- 第一个同名候选不符合等级或舰种时仍被直接点击。

### 4.5 准备页四级快照

准备页识别按物理槽位保存 `name`、`occupied`、`ship_type` 和 `level`，分四级有限执行：

1. LEVEL1 使用首张截图执行全局舰名 OCR 和血量占用检测；
2. LEVEL2 重新截图，为未知舰名槽位执行单槽识别，并首次读取全部占用槽位的舰种和等级；
3. LEVEL3 再次截图，只重试仍未知字段及严格规则下已经明确识别错误的字段；
4. LEVEL4 使用最后一张截图补未知舰名，仅为新确认规则读取实际需要的未知详情。

字段独立合并：已知值遇到后续 `None` 时保持不变；只有未知字段允许使用新结果补齐。
严格规则的错误详情可以在下一阶段清空并重试，宽松规则不会因此触发严格详情重试。

### 4.6 换船门禁与主选托底

- 已在编队且满足当前规划的主选或备选严格约束时，槽位加入 `verified_slots`；
- 当前满足候选或姓名仍未知时，按 YAML 顺序选择可用备选，先建立确定的托底状态；
- 备选成功后仅回查主选一次，找到则替换，找不到则保留备选；
- 无备选时主选也只搜索一次，失败后明确终止当前槽位流程；
- 候选避开其他槽位已经预留的舰船，失败记录只在本轮换船内有效。

这套门禁不以“多试几次”掩盖 OCR 问题，而是将每条路径限定为可证明会结束的状态流。

## 5. 风险与边界

- 当前坐标只针对 1280x720 界面完成实测，其他分辨率需要重新校准；
- 测试覆盖已采集的舰种和等级样本，不代表未出现字体状态的绝对正确率；
- 模型资源增加约 31.1MB 包体积；
- 增强开关默认关闭，可在出现兼容问题时直接回退到原 EasyOCR 链路；
- 实机截图样本未随 PR 提交，防止仓库体积继续增长；核心路由、坐标、解析和卡片绑定
  行为由单元测试覆盖；
- 智能换船一期依赖 FastOCR 识别 PR #536，合入前保持 Draft，并在依赖合入后重放验证；
- 多级快照增加有限截图次数，但最坏执行次数固定，不会形成无限 OCR 或换船循环。

## 6. 拆分 PR 范围

本次完整改造拆分为两个可独立审查的 PR：

- #536：FastOCR 引擎、PP-OCRv6-small 模型、区域校准、卡片坐标绑定和候选卡片校验；
- #537：首次快照门禁、四级 OCR 累积、主选无法确认时的备选托底和有限回查。

#537 不包含换船模块拆分、船库同步、OCR 样本采集工具、每日弹窗和 API 改动。模块
拆分将在行为修复稳定并合入后单独提交，避免重构与逻辑变化混在同一轮审查中。
